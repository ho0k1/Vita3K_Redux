# План: производительность и стабильность (принцип «короткие простые шаги»)

Идея: ничего тяжёлого не делать одним большим куском в критичном потоке. Работу
режем на мелкие шаги, растягиваем по времени и меряем. Часть этого уже сделана
(поэтапная очередь PKGj, фазы VFG, ограничение GPU-времени).

Правило плана: сначала измерение, потом правка. Каждый этап заканчивается
логами с телефона (S22+) и решением, идём ли дальше.

## Этап 0. Измерения (основа всего)
Лёгкое измерение, пишется в обычный лог, на FPS почти не влияет.
- Время создания шейдера и пайплайна в игре (всё дольше 5 мс).
- Кадры длиннее 40 мс с меткой причины: компиляция, остановка мира, ожидание GPU,
  ожидание present.
- Длительность каждой «остановки мира» (WorldStopScope) и размер перехода памяти.
- Температурный статус и частота кадров по минутам.
Результат: таблица «что реально даёт просадки» для DOA5 и ещё 1–2 игр.
Критерий готовности: логи с игры показывают причину каждой просадки >40 мс.

## Этап 1. Шейдеры и пайплайны без заиканий
Делаем только если этап 0 показал, что просадки из-за компиляции.
- Компиляция в фоне пулом потоков, а не в потоке рендера.
- Пока пайплайн не готов, кадр рисуем упрощённо или повторяем предыдущий.
- Прогрев кэша: при первом запуске игры компилировать наборы пайплайнов из кэша
  маленькими порциями в загрузочных экранах.
Критерий: на тех же сценах нет кадров >40 мс из-за компиляции.

## Этап 2. Остановки памяти короче
Делаем только если этап 0 покажет длинные остановки (в PKGj видели ~50 мс).
- Расширять память блоками меньше 16 МБ или заранее, в простое.
- Не ждать непаркованные потоки дольше порога.
Критерий: остановка мира не длиннее 10 мс.

## Этап 3. Тепло и энергия: адаптивная нагрузка
Используем уже существующий [THERMAL] статус Android.
- При росте температуры по ступеням: сначала генерация кадров (VFG), затем
  снижение разрешения, затем ограничение частоты кадров.
- Возврат ступеней назад с гистерезисом, без дёрганья.
- В настройках: переключатель «Адаптивный режим» (по умолчанию включён) и
  понятная иконка/подпись, когда он что-то снизил.
Критерий: 30 минут игры без падения ниже целевых FPS и без сильного нагрева.

### Динамическое разрешение (идея пользователя, 19.11) — РЕАЛИЗОВАНО
Сделано: ступени 0,5× до 1×, переключение по THERMAL и по темпу кадров, масштабирование цветных поверхностей на месте (blit), откат при сбое, маркер-файл против циклов падений. Ждёт проверки на устройстве. Ниже исходный план.

Обновление 21.11: на нагрев отвечает только разрешение (лимитер кадров убран). Реакция раньше, пока ОС ещё не сбросила частоты: THERMAL 2 (MODERATE) через 5 с, THERMAL 3 (SEVERE) через 2 с, шаг каждые 15 / 8 с. Прогноз нагрева (`PowerManager.getThermalHeadroom(10)`, API 30+, опрос раз в 2 с): значение ≥0,9 считается как THERMAL 2, ≥1,0 как THERMAL 3, то есть разрешение падает за ~10 с до того, как система начнёт сбрасывать частоты; в логах `[THERMAL] forecast` и `headroom=` в `[TICK]`. Пол снижен с 1× до 0,75× (VSS растягивает картинку), максимум 4 ступени.

Данные DOA5 @2.5×: ~60 fps держится, пока телефон холодный; после `THERMAL status 3`
кадр растёт с 17 до 26–39 мс. Снижение внутреннего разрешения вместо троттлинга — верный ход.
Сложность: `res_multiplier` зашит в размеры поверхностей (~80 мест в Vulkan-рендерере),
в шейдерные uniform'ы и кэш поверхностей, живой смены нет. План по шагам:
1. Ступени (напр. 2.5 → 2.0 → 1.5), переключение только на границе сцены/загрузки и только
   по `THERMAL >= 3` или по p95 кадра > цели 5 окон подряд; возврат вверх с гистерезисом 60 с.
2. Смена = остановка мира + сброс кэша поверхностей (как при переходах памяти), затем новое значение.
3. Всё за переключателем «Адаптивное разрешение»; в логе `[ADAPT]` на каждую смену.
Риск: графические артефакты после сброса кэша; поэтому сначала только по THERMAL, потом по кадру.

## Этап 4. Ровный вывод кадров
- Распространить темп вывода из VFG на обычный режим (без генерации кадров).
- Выровнять «хвост» кадров: не показывать два кадра подряд за один vblank.
Критерий: график длительности кадров без пиков >1.5× медианы вне загрузок.

## Этап 5. Работа в потоках UI Android
Проверка, что тяжёлые вызовы JNI и чтение диска не в главном потоке.
- Аудит экранов (список игр, сохранения, трофеи) на блокирующие вызовы.
- Перенос найденного в фон, мелкие порции.

## Не делаем
- Переписывание JIT (Dynarmic): гость и хост уже ARM, выигрыш небольшой, риск
  стабильности большой.

## Порядок и риски
0 → 1/2 (по данным) → 3 → 4 → 5. Любая правка шейдеров и памяти идёт за флагом
в настройках, чтобы можно было вернуть старое поведение без новой сборки.
