# Апскейл VSS и генерация кадров (VFG): исследование и план

> Исторический документ: и VSS, и VFG уже реализованы и по умолчанию включены (см. README, разделы «VSS» и «VFG»). Ниже исходное исследование.

## Что уже есть
**VSS** (фильтр экрана, Vulkan, `render_main_vss.frag`) — однопроходный апскейл с учётом контуров и подчёркиванием резкости. За основу взят Snapdragon Game Super Resolution 1 (Qualcomm, лицензия BSD-3, совместима с GPLv2), портирован на GLSL 4.50: константы окна берутся из `textureSize`, режим фиксирован RGBA. Включается в «Настройки → Графика → Фильтр экрана → VSS». Не проверено на устройстве.

## Что нашлось на GitHub и в новостях
| Решение | Подходит? | Почему |
|---|---|---|
| [SGSR 1](https://github.com/SnapdragonStudios/snapdragon-gsr) (пространственный) | да, уже взят | один проход, нужна только картинка |
| SGSR 2 (временной) | нет | нужны векторы движения и глубина, у кадров Vita их нет |
| LSFG / LSFG-Android (Lossless Scaling) | нет | шейдеры закрытые, нужна платная копия; на Android работает захватом экрана, +50–80 мс задержки |
| FidelityFX FSR3 Frame Generation | частично | нужны векторы движения из движка; есть отдельный проход оптического потока (MIT), его идею можно взять |
| FFmpeg Vulkan FRUC | нет | только NVIDIA Optical Flow SDK |
| RIFE и другие нейросети | нет | тяжело для телефона и нужен свой рантайм |

Вывод: готового открытого решения для Android нет. Реалистичный вариант — свой оптический поток на compute-шейдерах: блочное сопоставление по пирамиде яркости, фильтр выбросов и двунаправленное смешивание с проверкой согласованности (для закрытий — откат на ближайший кадр). Для игр Vita на 30 кадров это даёт 60 при разрешении 960×544.

## Как устроен показ кадров у нас (причина осторожности)
- `render_loop` (`renderer/src/batch.cpp`) в одном потоке обрабатывает команды GPU игры и вызывает `render_frame` + `swap_window`.
- Кадр показывается, когда игра переключила буфер (`new_frame`), а не по таймеру vsync.
- Поэтому для вставки промежуточного кадра нужно показывать его с задержкой в полпериода, не блокируя поток обработки команд, иначе игра замедлится. Нужен либо планировщик показа внутри цикла, либо отдельный поток показа с общей очередью.
- Данные кадра не имеют номера: понадобится счётчик в `update_prediction` / `new_frame`, чтобы отличать новый кадр от повтора.
- Цена: +1 кадр задержки (интерполяция показывает промежуточный между прошлым и текущим, текущий идёт следом).

## План этапов (каждый за выключенным по умолчанию параметром)
1. Счётчик кадров и копия последних двух кадров в приватные изображения (без изменения картинки).
2. Compute-шейдеры: пирамида яркости, поток 8×8 с поиском ±8, фильтр, интерполяция. Проверка шейдеров на тестовых кадрах на хосте (lavapipe).
3. Планировщик показа: промежуточный кадр в середине периода, откат на обычный показ при пропуске кадра, смене сцены, паузе и меню.
4. Параметр в настройках («Генерация кадров», только Vulkan), счётчики в логе: время работы GPU на кадр, число откатов.
5. Проверка на S22+: качество (HUD, края, закрытия), температура, задержка.

## Риски
- Артефакты на быстрых сценах, тексте и 2D-играх с повторами текстур (поток ошибается).
- Лишняя нагрузка на GPU Adreno 730, около 1–2 мс на кадр при половинном разрешении потока (оценка, не измерение).
- Изменение цикла показа затрагивает всё; поэтому только за параметром и с откатом.
