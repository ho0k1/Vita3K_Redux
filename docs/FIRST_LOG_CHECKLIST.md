# Что проверить в первом логе новой сборки

Сборка должна включать локальные коммиты после cc34caf (адаптивное разрешение, прогноз нагрева, замер GPU, метрика подачи).
Играть 10+ минут в DOA5 до нагрева, лог из `sessions/app_*.log` (+ скриншот, если пропали текстуры).

## 1. Чёрные текстуры при смене разрешения
- `[ADAPT] internal resolution A -> B` и сразу после: `[ADAPT] N color surfaces rescaled in place, M dropped`.
- Хорошо: `dropped 0`, персонаж не чернеет. Если `dropped > 0` или чёрное осталось: в логе будет причина (`cannot allocate`), тогда следующий шаг — масштабировать и depth-буферы.
- Нет ли `[TEXMEM] ... texture budget ... -> 256 MiB` рядом по времени (нехватка памяти — отдельная причина).

## 2. Реакция на нагрев
- `[THERMAL] forecast headroom X -> Y`: приходит ли прогноз (не −1) и опережает ли он смену статуса THERMAL.
- Шаги разрешения при THERMAL 2 / прогнозе ≥0,9 (через ~5 с) и THERMAL 3 / ≥1,0 (через ~2 с).
- Нет ли замедления вдвое: период кадров из `[PERF] 10s` и `[ADAPT] status`.
- Возвращается ли разрешение вверх после остывания (`[ADAPT] status:` раз в минуту; прогноз не должен висеть ≥0,9 постоянно).

## 3. Замер GPU
- В `[ADAPT] status:` поле `GPU busy N%`: не −100% (то есть замер работает).
- Строка `frames are slow but the GPU is only N% busy` означает, что узкое место CPU: тогда разрешение не снижалось сознательно.

## 4. Подача кадров (решение по Этапу 4)
- `[PERF] pacing: ... irregular N (P%)` каждые 10 с. При стабильных fps доля неровных должна быть единицами процентов; больше — делать подачу по `VK_GOOGLE_display_timing`.

## 5. Остальное
- `[PERF] 10s`: медленные пайплайны (`slow`) не вернулись к 10+ при первом запуске игры (кэш не сбросился).
- Нет ли `[ADAPT]` с ошибками, нет ли падений при смене разрешения (маркер в `cache_path` удаляется через 30 с).
- Служба загрузки PKGj: уведомление не пропадает, на Android 15+ нет краша через ~6 ч (`onTimeout`).

## 6. Второй лог (после первого DOA5-теста, 2026-11-22)

Первый лог показал: THERMAL 3 с запуска, GPU занят 12–20%, просадки идут от очереди гостевых потоков на ядре 2
(`[CORELOCK] core 2`: 3,5–7,4 с суммарного ожидания за 10 с, ждут `ATStreamEngine`, `ATStreamPlayer`, `Accessory`, `TFW::Physics`).

В новой сборке проверить:
- `[CORELOCK] audio streaming threads (ATStream*) are exempt ...` есть в начале игры; суммарное ожидание на core 2 (`wait_total_ms`) стало заметно меньше, `max` ниже 100 мс. Откат: пустой файл `core_lock_strict` в папке данных эмулятора.
- `[PERF-HINT] performance hint session created for N thread(s)` (Android 14+ добавляет потоки позже; на Android 13 сессия остаётся из первых потоков). Если написано `NOT available`, подсказки планировщику не сработали.
- `[ADAPT] thermal 3 but the GPU is only N% busy: keeping the resolution`: разрешение не должно падать до 0.75x при простаивающем GPU.
- `[PERF] 10s` `>=50ms` и `irregular` в `[PERF] pacing` стали меньше, чем в первом логе (≈ 6–20 / 7–53%).
- sustained performance mode сознательно не включён: он ограничивает пиковую частоту и мог бы снизить средний fps. Решать по этому логу.
